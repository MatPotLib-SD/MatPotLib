How the repo is divided

Five code modules, each built against a contract rather than against each other. The seams are the design — a pot that only knows one endpoint, an app that only knows REST, and a backend that is the sole holder of the database’s service-role key.

The module map

Every box is either a directory in this repo or a service it depends on. Every arrow is a contract that outlives whichever module is being rewritten on either side of it.

What crosses each boundary

Eight seams, and each one is enforced by a named piece of code rather than by convention.

Inside the backend

The largest module divides again, into nine NestJS modules that fall into three shapes. Only two of them talk to a sibling — the rest reach straight through to Postgres.

The modules, one by one

C++ · PlatformIO

firmware/

The pot. Reads three sensors over I²C and analog, then posts over HTTPS. Knows one URL and one secret; knows nothing about users, plants, or species.

  • src/main.cpp — connectWiFi, postReading, loop
  • include/secrets.h.example
  • platformio.ini — arduino_nano_esp32
TypeScript · NestJS

backend/

The only component with write access to the database. Validates both credential types, evaluates readings against species ranges, and owns every business rule.

  • src/ — 9 modules, guards, DTOs
  • test/ — unit + e2e with Expo mocked
  • Dockerfile → ACR → Container Apps
TypeScript · Expo RN

app/

The phone. A session gate routes to auth, onboarding, or tabs; screens poll the backend for readings and alerts. Written against the spec’s endpoint list before the backend existed.

  • api/ — client.ts, supabase.ts
  • navigation/ — Root, Auth, Tab
  • screens/ hooks/ components/ types/
SQL · TypeScript

db/

The shape of the data, versioned. One migration defines all 8 tables with RLS and indexes; an import script loads the dataset every alert threshold is compared against.

  • supabase/migrations/ — init.sql
  • import_miflora.ts — 5,335 species
  • SCHEMA.md — column-level reference
TypeScript

scripts/

Hardware, simulated. Lets the backend, app, alerting, and push path all be exercised end to end with no pot on the desk — the reason a firmware blocker never stalled the build.

  • sim_device.ts — posts live readings
  • seed_demo.ts — user, device, plant, 48 h
  • trigger_alert.ts — forces out-of-range
YAML · Markdown

.github/ + deploy/

Build and release. CI lints, builds, and tests both TypeScript modules on every push; the deploy workflow pushes an image to ACR. Rollout stays manual — the university tenant blocks the service principal CI would need.

  • workflows/ci.yml — backend + app jobs
  • workflows/deploy.yml — docker → ACR
  • deploy/azure/ and DEPLOYMENT.md

Why it divides this way

The contracts were written before any of the code. docs/HANDOFF.md landed as a 439-line spec in the first feature commit, pinning the schema, every endpoint, and both auth mechanisms up front. That is what let the modules be built out of order and integrated afterward — the app was written against the endpoint list before the backend implementing it existed, and it worked because neither side was inventing the seam. The modular split above is that spec, made out of directories.
